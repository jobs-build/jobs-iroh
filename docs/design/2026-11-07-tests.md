# Tests: TESTS.jobs, test identity by resolved inputs, test-passed memo

Date: 2026-11-07
Status: accepted design (implemented in the same arc)
Scope: one arc — a `TESTS.jobs` recipe next to `BUILD.jobs`, the `test()`
entry with the directory's own build available as an input, two new
scheduler kinds (`testvalue`, `testrun`), the output-resolved test identity
KT, the `test-passed` memo refs, `jobs-client test` / `remote-test`, and
the runner ALPN fence.

## 1. Problem and reframing

A build system that memoizes builds by content still re-runs tests on every
commit — or has no notion of tests at all. jobs-iroh had the latter. The
request: run tests defined in `TESTS.jobs`, treat them like a build (same
sandbox, same inputs machinery, same scheduler), produce **no output**,
but **record the fact that they ran** so an unchanged test is never run
twice. The test gets the **build output as an input**.

The last point decides the identity design. A build's run identity KP is
`{pinned job, platform, v, covered src/}` where the pinned job carries every
input's *definition*. A build-of-this-directory definition embeds the whole
source tree's key, so under KP-keying a docs-only edit would re-key the
test's `build` input definition and re-run the tests even though the build
output — a KP memo hit — is byte-identical. The memo would be nearly
useless for exactly the tests the feature is for.

So tests are keyed by **what the sandbox actually sees**: KT = key of
`{script, env, dir, caches, covered src/, platform, v, inputs resolved to
their content keys}`. Input *definitions* do not enter KT; input *outputs*
do. A test re-runs iff its script, environment, covered sources, platform,
or any input's bytes changed. This is the identity a test wants; builds keep
KP (changing their memo key is out of scope and would re-key every cached
output).

## 2. Decisions of record

| Decision | Choice |
|---|---|
| Recipe | `TESTS.jobs` in the build dir; `def test()` returns the same struct as `build()` minus `runtime_deps` (an error if present); `plugins()` allowed exactly as for builds. |
| The build as an input | A predeclared `build` Input value in test recipes: the build of the **same (context, dir, platform, params)** with the default `BUILD.jobs`. Explicit (`inputs = {"app": build}`) — a test that doesn't list it doesn't build it. |
| Definition | `builddef.Definition` gains `Test bool` (`cbor:"test,omitempty"`); `BuildFile` keeps its meaning (recipe path relative to dir, default `TESTS.jobs` for tests). K differs from the build's K by construction. |
| F | The test F-tree always splices the effective recipe as a top-level `TESTS.jobs` entry (`amber.TestFromTree`). The entry's presence is the marker the eval stages branch on; a build F-tree never has one, so F_test ≠ F_build even for byte-identical recipes. |
| Stages | `testvalue(K)` → `buildfrom(K)` → `pluginresolve(F)` → `pin(F)` (the three middle kinds are **shared** with builds, test-aware via the F-tree) → inputs → `testrun(KT)`. |
| KT | `{job.cbor = canonical builddef.TestJob, platform, v = amber.KPVersion, src/ = the KP tree's src/}` — assembled by `cover.DeriveTest` after every input is done. Resources are deliberately excluded (bumping memory for a passed test must not re-run it). |
| Doneness | `test-passed:<KT>` → KT (the memo), `test-passed:<F>` → KT (the alias the fast-path and the client read). Failed tests leave no ref: they re-run on the next submit. |
| Derived refs | `build-pinned:<KT>` (alias of the pinned blob; unfold, gate and the runner read it unchanged) and `kt-tree/<KT>` (pull carrier). Re-derived on demand like the KP refs. |
| Output | None. `$out` exists and is discarded. Logs ride the usual log ring; failures the durable FAILURES trail. |
| Timeout | `test()` takes `timeout = "<Go duration>"` (whole seconds, ≥ 1s); omitted = **5 minutes** (`runner.DefaultTestTimeout`). Enforced by the runner as a context deadline on the sandbox (§6.1): a timed-out test is a hard failure with no ref. Rides `Pinned.TimeoutSec`; like resources it is NOT part of KT. `build()` rejects the field — builds stay unbounded. |
| Fence | Runner ALPN `jobs-runner-nats/3.0 → 4.0` (§7). |
| Client | `jobs-client test` (local, Linux), `jobs-client remote-test --server` (push, submit, watch, pull the `test-passed` marker home so a later local `test` memo-joins). |

## 3. Recipe surface

```python
# TESTS.jobs, next to BUILD.jobs
def plugins():            # optional, as for builds
    return {"go": imp(fetcher = GOPLUGIN, params = {})}

def test():
    toolchain = imp(fetcher = "tarball+https", params = {...})
    return struct(
        inputs    = {"app": build, "toolchain": toolchain},
        env       = {},
        script    = '"$(jq -r .app <<<"$JOBS_DEPS")/bin/jobs-client" --version',
        closure   = ["//cmd", "//go.mod"],       # optional, as for builds
        caches    = {"/go-build-cache": "..."},  # optional
        resources = struct(cpu = "2000m", memory = "4Gi"),
        timeout   = "10m",                       # optional, default 5m
        name      = "jobs-iroh tests",
    )
```

- `build` is an `Input` of kind build: `{source: tree(context or build
  root), dir, platform, params (the test's own), ctx}` — exactly the
  definition `jobs-client build`/`remote-build` of the same directory
  constructs, so the test joins the user's own build node. Predeclared at
  both eval stages (Starlark resolves names at compile time).
- `runtime_deps` is rejected: a test has no output to ship a closure with.
- `timeout` is a Go duration string in whole seconds, at least `"1s"`;
  omitted means the runner's 5 minute default (§6.1). `test()`-only:
  `build()` rejects it rather than ignoring a limit the author wrote.
- Everything else (`sources`, `closure`, `generated`,
  `sources_allow_escaping`, `caches`, `resources`, `name`, `source.read`,
  `imp`, `bld`, `subbuild`, `deps`, `plugins[...]`) behaves as in `build()`.
- The sandbox contract is the build one: `$SRC`/CWD at the covered dir,
  `$SRC_ROOT`, `/jobs/store/<BOK>` for every input, `JOBS_DEPS`, `$out`
  (ignored), no network. Exit 0 = passed; anything else = failed (hard).

## 4. Identity

### 4.1 K and F

K = key of the canonical definition with `test: true`. The old-server
canonicality check strips the unknown field and rejects the def loudly
(the `ctx` precedent).

F-tree for a test: `{env/, dir?, params, platform, TESTS.jobs}` — the
recipe is **always** spliced (no join-preserving omission: the entry is
the mode marker). `loadBuildFromEnv` reads the top-level `TESTS.jobs` first
and sets `Test`; `RunPluginResolve`/`RunPin` pass it into the recipe
evaluator, which predeclares `build` and calls `test()`.

### 4.2 KT

```go
type ResolvedInput struct {
    Name string `cbor:"name"`
    Kind string `cbor:"kind"`
    Out  []byte `cbor:"out"`            // BOK: the c/ artifact for a build, the output tree for an import
    Deps []byte `cbor:"deps,omitempty"` // build-output-deps tree key (builds only)
}
type TestJob struct {
    Inputs []ResolvedInput   `cbor:"inputs"`
    Env    map[string]string `cbor:"env"`
    Script string            `cbor:"script"`
    Caches []PinnedCache     `cbor:"caches,omitempty"`
    Dir    string            `cbor:"dir,omitempty"`
}
```

KT tree = `{job.cbor (canonical TestJob), platform, v, src/}` via the same
`BuildKPTree` assembler, `src/` spliced by key from the KP tree (so the
prune/normalize semantics and their version `v` are shared). Inputs are
resolved by `cover.ResolveInputs` — the same ref reads the runner's
`collectStore` performs (`import-output:K`, `build-from:K → F →
build-output:F → c/`, `build-output-deps:F`). **[INV]** `cover.DeriveTest`
is identity-critical shared code: the server and the local pipeline run the
same function (cross-path golden test).

Accepted edge: a non-reproducible build rebuilt between KT derivation and
the test run (GC expiry + rebuild) can hand the runner different bytes
than KT was derived from. The runner resolves by ref name, as everywhere.

### 4.3 Refs

| Ref | Written by | Points at |
|---|---|---|
| `test:K` | server submit (bookkeeping, the `build:K` analogue; the registry's tag listing skips these Ks) | the def |
| `build-pinned:<KT>` | server KT derivation / local pipeline | the pinned blob |
| `kt-tree/<KT>` | same | KT (pull carrier) |
| `test-passed:<KT>` | testrun commit (gated) | KT — **the doneness marker and the memo** |
| `test-passed:<F>` | server alias on testvalue advance-to-done / local pipeline / remote-test pull-home | KT |

GC: no protected class, no family coupling. Expiry of either `test-passed`
ref only costs a re-run (rebuild-safe by the same argument as
`build-output`).

## 5. Scheduler

- `testvalue` (orchestrator, never placed): doneness fast-path
  `build-from:K → F → test-passed:F`. `advanceTestValueLocked`: require
  `buildfrom` → resolve F → `pluginresolve` → `pin` → `resolveKPLocked` →
  read `build-pinned:<KP>` and **require every pinned input under the
  testvalue itself** (imports → `import_K`, builds → `buildvalue_K`; the
  cycle check applies) → when every dep is done, `deriveKT` (idempotent;
  writes `build-pinned:<KT>`, `kt-tree/<KT>`) → require `testrun(KT)` →
  on done write `test-passed:F` → done.
- `testrun` (placeable, KT-keyed): unfold reads `build-pinned:<KT>` exactly
  like buildrun (resources, caches, inputs — all already done); PullRefs =
  `kt-tree/<KT>` + `build-pinned:<KT>` + shell + input outputs (+deps) +
  present caches; gate row: `test-passed:<KT>` + declared
  `build-cache:<id>:<platform>`; requirement default = the build default.
- `waiterFs` (FailureRecord.ForF), `requirementLocked` (request resources
  reach the target's stages), `applyRecipeLabelLocked` (the `name=` label
  relabels testvalue dependents) all treat testvalue like buildvalue.
- Submit: `def.Test` picks the target kind and the `test:K` bookkeeping
  ref; `api.RequestInfo.Test` (additive) marks the request.

Memo-hit walk-through (docs-only commit): new K, new F → buildfrom, resolve
and pin run (eval churn, as for builds) → KP unchanged → the `build` input's
new K → its own chain memo-hits on KP → same BOK → **same KT** →
`test-passed:KT` exists → testrun fast-paths done (`Cached`) → alias → done.
Tests do not run.

## 6. Runner and local pipeline

- `runner.RunTest(ctx, st, rw, brc, ex, kt)`: `assembleBuildSpec` on
  `build-pinned:<KT>` with `SourceKey: KT, SourceDir: "src"` (the KT tree
  is KP-shaped, so nothing changes), run the script, non-zero exit → hard
  failure, success → finalize caches, remove the work tree, publish
  `[caches…, test-passed:<KT> → KT]`.
- `runnerd.driveStage` dispatches `testrun`.
- Local: `runner.TestFromSource` = `localBuildFrom` (test mode) +
  `driveTestStages`: `test-passed:F` fast-path; else resolve/pin as builds;
  `ensureInputs`; `deriveKP`; `cover.DeriveTest`; `test-passed:KT`
  fast-path (alias written) or `RunTest` (alias written after). Progress
  step `test` (`(cached)` on a memo hit).

### 6.1 Timeout

A test run is bounded by `Pinned.TimeoutSec` — the recipe's `timeout`, `0`
meaning `runner.DefaultTestTimeout` (5 minutes). `RunTest` runs the executor
under `context.WithTimeout`: past the limit the sandbox child — PID 1 of
its own pid namespace — is SIGKILLed and the whole process tree with it,
the executor returns the signalled exit, and the verdict is the hard
failure `testing: timed out after <limit>` plus the stderr tail, with no
ref, so the test re-runs on the next submit like any failure. A parent
cancel is reported as a cancel even past the deadline; an exit 0 that races
the deadline is still a pass. Builds have no limit (`build()` rejects the
field); the test default exists because a hung test would otherwise hold
its runner slot forever — the JetStream lease is heartbeat-extended for as
long as the process lives. The limit is not identity: it rides
`build-pinned` like resources and is absent from `TestJob`, so raising it
for a passed test does not re-run it. Pinned records written before the
field decode with `TimeoutSec = 0` and get the default.

## 7. Compatibility and fencing

- Old server ← new client test submit: rejected at the canonicality check
  (unknown `test` field), loudly.
- Old runner ← new server: `buildfrom` decodes the def without `test`,
  assembles a **build** F-tree (`BUILD.jobs`) and commits
  `build-from:K_test → F_build` — the gate is name-keyed, so the wrong
  binding would stick and the test pipeline would pin and run the build
  script as the test. Wrong results, not clean errors ⇒ **[INV] ALPN bump
  `jobs-runner-nats/3.0 → 4.0`**. A new runner cannot connect to an old
  server either (it would be handed nothing it can't do, but the fence is
  symmetric by construction).
- Existing refs, KP bindings, KPVersion: untouched. No `KPVersion` bump —
  no existing Pinned derives differently.
- `wire.ParseNodeName` accepts the two new kinds (fail-closed set).

## 8. Client

- `jobs-client test [--source] [--dir] [--test-file] [--platform]
  [--param]…`: context resolution searches for `TESTS.jobs` (or
  `--test-file`) with the same repo-root rules as `build`; prints
  `test:    <F>` and `passed:  <KT>`; exit 1 on failure.
- `jobs-client remote-test --server …` mirrors `remote-build`: push, submit
  the test def, TUI/classic watch, then on `done` pull `build-from:K` (→F)
  and `test-passed:F` (→KT) home and write `test-passed:<KT>` locally, so a
  later local `test` of the same tree is a memo hit.
- TUI/watch: a testvalue row folds like a buildvalue row with the terminal
  stage named `test`; direct input rows hang under the testvalue (its
  inputs are its own deps). `status` gains a KIND column.

## 9. Non-goals

- Keying **builds** by resolved inputs (would re-key every cached output).
- Test output artifacts (reports, coverage): tests have no output by
  decision; logs and failure records are the observability.
- Running tests as part of `remote-build`/`build` automatically.
- A `test` input kind (tests as dependencies of builds or other tests).

## 10. Testing

- `builddef`: `Test` round-trips canonical; `TestJob` canonical encode.
- `wire`: new kinds parse.
- `amber`: `TestFromTree` differs from `BuildFromTree` on the same env +
  recipe; deterministic.
- `recipe`: `test()` evaluation, `build` predeclared equals the expected
  definition (root and widened), `runtime_deps` rejected, no-`test()` error.
- `cover`: `DeriveTest` deterministic; same resolved outputs under
  different input definitions ⇒ same KT; different output ⇒ different KT.
- `sched`: testrun gate rows; testrun pull refs; full chain through the
  fake runner (refs written, inputs required under the testvalue); memo
  resubmit (nothing re-runs); derived-ref heal; **KT stability** — a second
  test def over a different tree whose pinned script and input output agree
  ⇒ testrun fast-paths done (`Cached`).
- `runner` (Linux e2e): `TestFromSource` with a `TESTS.jobs` that mounts
  `build`; second run cached; uncovered edit ⇒ build and test cached;
  covered edit ⇒ test re-runs; failing script ⇒ error, no `test-passed`.
- `tui`: fold of a testvalue snapshot.
